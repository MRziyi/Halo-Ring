## 1. Why this refactor exists

### 1.1 Live-burn-in findings

| Finding | Severity |
|---|---|
| Main-app ring navigation feels broken (SWIPE_UP/DOWN do nothing visible) — root cause is the over-engineered `InAppFocusController` (focus-management abstraction we wrote) not reliably grabbing initial focus | 🔴 blocker |
| Settings menu is too deep for AR glasses use — 10+ top-level items, no visual hierarchy | 🟡 UX |
| Several features remain unimplemented despite SPEC v3 unlocking them: sport sessions, accel-driven spatial events, capability-aware UI gating | 🟡 feature gap |

### 1.2 User invariant

The wearer's mental model is:

> **Ring = temple-touchpad extension.** The 4 base gestures (TAP / DOUBLE_TAP /
> SWIPE_UP / SWIPE_DOWN) MUST trigger the **same system behaviour** as the
> equivalent temple actions — they're a wireless extension of the same physical
> control surface, not a separate app with its own UI conventions.
>
> Custom gestures (TRIPLE_TAP, QUADRUPLE_TAP, LONG_PRESS, all the combos) are
> **the ring's value-add** — the project's flagship feature. They're fully
> programmable per profile + extendable via the Doc/18 plugin protocol.

Source: Zack 2026-05-27.

### 1.3 What the doc audit confirmed (and what surprised us)

A documentation audit (run 2026-05-27, see commit `19f2824` for context) graded
each Doc/01..18 file against the post-burn-in reality. The headline verdict:

> *"The architecture is fundamentally sound. The refactor is a focus+polish
> effort, not a redesign."*

The audit identified **6 gems** that must survive:

1. **12-gesture vocabulary + GestureSynthesizer** (Doc/05) — fully tested,
   elegant; the multi-tap/combo state machine is the spine of the "custom
   gestures" feature
2. **4 default profiles** (Doc/05 §4) — Navigation / Media / Reader / Fast;
   auto-switch by foreground app, manual cycle
3. **Profile editor + Action Picker + System Gestures** UI (Doc/08) — the
   actual customization surface; this IS the product
4. **Plugin protocol** (Doc/18) — external apps register actions, ring profiles
   bind to them; Constellation is the first live client
5. **HUD overlay + gesture-hint HUD** (Doc/05 §2, Doc/08) — fast visual
   feedback for ring gestures; explicitly named a project highlight
6. **4-strategy pattern** (Doc/04 §4) — DisplayAdapter / GlassActionMapper /
   WearStateProvider / FeatureIntents — cleanly abstracts Rokid vs RayNeo

The audit identified **3 dead-weight sections** (mostly documentation drift, not
code rot):

1. Doc/02 sections 0–7 (protocol tables) — now superseded by SPEC v3; should be
   short integration notes, not a duplicate source of truth
2. Doc/07 §1.1 sensor matrix — many `🟡 TBD` rows that SPEC v3 already verified
3. Doc/13 §"Phase-0 test plan" — historical now; the actual test plan moved to
   `R08-dev/phase0/`

So the refactor is **small in code, modest in docs, zero in architecture**.

## 2. Non-goals

To prevent scope creep, this refactor does NOT:

- ❌ Delete the 4 default profiles (Navigation / Media / Reader / Fast)
- ❌ Delete Profile editor, Action Picker, or System Gestures customization
  screens — these ARE the product
- ❌ Delete the Plugin protocol (Doc/18) — Constellation already integrates
- ❌ Delete the 4-strategy pattern or the RayNeo flavor — both stay
- ❌ Delete Test Arena — it's how users learn their custom gestures
- ❌ Delete the HUD overlay or any of its 6 event variants
- ❌ Touch `:core` gesture state-machine logic (`GestureSynthesizer`,
  `InteractionRouter`, `ActionRouter`) — they're load-bearing and tested

What we WILL do is listed in §3.

## 3. The 6 phases

### P1 — Base gestures → system KeyEvent passthrough 🔴 blocker

**Goal**: fix the main-app navigation breakage by treating the 4 base gestures
as a thin layer over Rokid's temple-touchpad KeyEvents.

**Background**: Rokid bare-metal docs §
[01-key-events](../../Constellation/reference/rokid-glass/bare-metal-docs/01-key-events.md)
specify that the temple touchpad fires standard Android KeyEvents:

- Touchpad single click → `KEYCODE_DPAD_CENTER`
- Right-temple key double click → `KEYCODE_BACK` (system-occupied, can't be intercepted)
- Touchpad swipe forward → series of `DPAD_RIGHT` + final `DPAD_DOWN`
- Touchpad swipe back → series of `DPAD_LEFT` + final `DPAD_UP`

The user's mental invariant (§1.2) maps the ring's 4 base gestures onto the same
KeyEvent stream, so wherever a temple gesture works (Sprite Launcher, third-party
apps, system Settings), the ring gesture works identically.

**Concrete changes**:

1. New `GestureConfig` fields:

   ```kotlin
   data class GestureConfig(
       // ... existing fields ...

       /**
        * When true, the 4 BASE gestures (TAP / DOUBLE_TAP / SWIPE_UP / SWIPE_DOWN)
        * fire system KeyEvents instead of profile-mapped GlassActions:
        *   TAP        → KEYCODE_DPAD_CENTER
        *   DOUBLE_TAP → KEYCODE_BACK
        *   SWIPE_UP   → KEYCODE_DPAD_RIGHT  (= temple swipe forward semantics)
        *   SWIPE_DOWN → KEYCODE_DPAD_LEFT   (= temple swipe back semantics)
        *
        * Custom gestures (TRIPLE_TAP, QUADRUPLE_TAP, LONG_PRESS, all combos)
        * continue to go through the profile mapping unchanged.
        */
       val useSystemKeyEvents: Boolean = true,

       /**
        * When [useSystemKeyEvents] AND this is true, SWIPE_UP / SWIPE_DOWN swap
        * their KeyEvents (SWIPE_UP → DPAD_LEFT, SWIPE_DOWN → DPAD_RIGHT). For
        * users who read "up" as "scroll up" rather than "next-in-sequence".
        */
       val reverseSwipeSemantics: Boolean = false,
   )
   ```

2. New `:app/.../ui/SystemKeyDispatcher.kt` — a thin object that holds an
   `Activity` ref (set in `MainActivity.onResume`) and exposes
   `dispatch(keycode: Int)`. Implementation: builds an `ACTION_DOWN`
   `KeyEvent`, calls `activity.window.decorView.dispatchKeyEvent(...)`,
   then `ACTION_UP`. Returns whether either dispatch was consumed.

3. `InteractionRouter` adapter — when resolving a base gesture, if
   `gestureConfig.useSystemKeyEvents` is true, call `SystemKeyDispatcher`
   instead of looking up the profile map. Custom gestures (everything else)
   continue through `profile.map[gesture] -> GlassAction -> ActionRouter`.

4. **Delete** the contents of `InAppFocusController.route()` for `NavPrev` /
   `NavNext` / `Confirm` / `Back` cases — they're now handled by
   `SystemKeyDispatcher`. The `focusOnTabStrip` flag goes away. The
   `tabController.prev()/next()` direct calls go away (Compose will route
   `DPAD_LEFT/RIGHT` to whatever is focused — including the TabBar).

5. The `auto-focus on app launch` LaunchedEffect added in burn-in stays — we
   still need *some* element focused for the system to know where to apply
   DPAD events. Compose's TabBar with its FocusRequester already handles that.

6. Tests: 6 new cases in `GestureSynthesizerTest` / new `SystemKeyDispatcherTest`.

**Acceptance**: in the rokid debug APK on a OnePlus burn-test rig, opening the
app and using ring SWIPE_DOWN navigates Compose focus down through visible
focusable rows; SWIPE_UP navigates up; TAP fires the focused row's `onClick`;
DOUBLE_TAP backs out (already worked).

**Effort**: ~150 LOC.

### P2 — Settings menu reorganization 🟡 UX

**Goal**: cut Settings depth from 10+ top-level items to ~5, keeping every
existing function.

**New top-level Settings layout** (in this order):

| Order | Item | What it groups |
|---|---|---|
| 1 | **Ring** | Pair / Re-pair, Find Ring, MAC/FW/signal/battery info, Forget |
| 2 | **Vitals** | Auto-snapshot interval, CSV export, Autonomous PPG toggle, Daily step target, "Pause when off-finger" |
| 3 | **Gestures** | (nested) Profiles list → Profile editor / Action Picker / System Gestures |
| 4 | **Plugins** | (nested) External Plugins (Doc/18) |
| 5 | **More** | (nested) Feedback / Power & Connection / Test Arena / Advanced / Language / About |

This collapses the current 10+ flat items into 5 disciplined sections. Every
sub-screen is reached in ≤2 taps (vs the current 1 tap but high-cognitive-load
"10 items to scan").

**Concrete changes**:

1. `SettingsRootScreen` rewrite — render 5 sections instead of the current
   flat list. Each section is a `ListRow` that pushes a sub-screen.
2. Three new "group" sub-screens: `GesturesGroupScreen`, `PluginsGroupScreen`
   (single-item; could be inlined), `MoreGroupScreen`. Each lists its members
   and pushes further.
3. `SettingsSection` enum reorganises — `SETTINGS_GROUP_GESTURES`,
   `SETTINGS_GROUP_MORE`, etc. The leaf-level `SubScreen` values (Feedback,
   ProfileEditor, etc.) stay unchanged.
4. No behavioural changes to leaf screens — they don't know they're nested now.

**Acceptance**: every previously-reachable Settings screen is still reachable;
top-level Settings shows 5 items not 10+.

**Effort**: ~200 LOC.

### P3 — Capability-gated UI 🟡 polish

**Goal**: hide features the ring's firmware doesn't actually support.

**Background**: SPEC v3 §3 verified that the ring publishes capability bitmaps
on connect (14-byte SetTime extension + 9-byte 0x3C response). audit-pass-y
already plumbed this into `AppGraph.ringCapabilitiesFlow`. Now use it.

**Concrete changes**:

1. `VitalsScreen` — gate the Stress row on `"hrv"` capability presence;
   gate BP row on `"bpSetting"` (most R08 units don't have this).
2. `VitalsPrefsScreen` — same gating for Stress prefs.
3. `RingScreen` — show a "Capabilities" expandable row listing which features
   the ring advertises.
4. `MainActivity` — pass `ringCapabilities: Set<String>` through to screens
   that gate.

**Acceptance**: on the burn-in unit (`R08_E600`, capabilities = `appMeasure /
bloodOxygen / hrv / newSleepProtocol / pressure / temperature / wechat / +9 more`),
Stress row + BP row are hidden in Vitals.

**Effort**: ~100 LOC.

### P4 — Sport session UI (0x77/0x78) 🟢 new feature

**Goal**: surface the firmware's workout-tracking capability to the user.

**Background**: SPEC v3 §4.8 + §10 — `0x77 [01, sport_type]` starts a session
on the ring; ring then pushes `0x78` ticks with duration + HR. Concurrent
`0x73 sub=0x12 ACTIVITY_TOTAL` push gives steps/distance/calories.
audit-pass-y already added `R08BleClient.startSportSession()` /
`stopSportSession()` methods.

**Concrete changes**:

1. New `RingEvent.SportTick` handler updates a `SportSessionState` flow:

   ```kotlin
   data class SportSessionState(
       val active: Boolean,
       val sportType: Int,
       val durationSec: Int,
       val hrBpm: Int?,
       val startedAtMs: Long,
   )
   ```

2. `VitalsScreen` adds a workout sub-section:
   - When `!active`: "Start workout" CTA + sport-type picker (Walk / Run / Cycle / …)
   - When `active`: live duration + HR + "Stop workout" CTA
3. Service handles `0x77 START` ack timestamps for the user's "started" display.
4. Beijing-locked timestamp adjustment already in place (SPEC §4.8) — verify
   the ack's u32_LE is interpreted correctly.

**Acceptance**: tap Start, ring's PhoneSport state engages (verified in logcat),
HUD shows live duration, tap Stop, totals saved.

**Effort**: ~300 LOC + a few strings.

### P5 — Spatial features from accelerometer 🟢 new feature

**Goal**: turn the now-decoded 0xA1 accel stream into useful UX signals.

**Background**: audit-pass-y added `AccelProcessor` with posture / free-fall /
impact / wrist-shake detection. Nothing in the app subscribes to its events yet.

**Concrete changes**:

1. Service starts the accel stream on a user toggle (Settings → Advanced →
   "Spatial features"). Default OFF — `0xA1 [01]` adds ~64 B/s of BLE traffic.
2. `AccelProcessor` events:
   - `FreeFall` → HUD alert "Ring dropped?"
   - `Impact` → log; no HUD by default (too noisy)
   - `WristShake` → optional gesture; bound by default to "Peek HUD" in
     System Gestures (mirrors `appType=7` Game-mode wrist-shake from SPEC §4.10)
   - `PostureChanged` → optional profile auto-switch trigger (palm-down →
     Reader profile? palm-up → Navigation? — leave as user choice via a new
     Profile field `autoActivateOnPosture: AccelProcessor.Posture?`)
3. Wire `accelProcessor.reset()` on disconnect (already in audit-pass-y).

**Acceptance**: with Spatial features ON, dropping the ring fires the HUD;
shaking the worn ring fires the configured gesture.

**Effort**: ~200 LOC.

## 4. Sequencing rules

- P1 ships **first** (it's the blocker) and **alone in its commit** — a
  pure-mechanic fix, easy to revert if it breaks anything subtle.
- P2 can ship in its own commit anytime after P1 (no dependency).
- P3 / P4 / P5 are independent of each other and can be parallelized across
  commits.
- P6 ships **last** (so the docs reflect the final shipped state, not in-flight
  intent).
- After each phase: full test run (`./gradlew :core:test`), both flavor debug
  APK builds, OnePlus burn-test smoke check (boot → pair → exercise the new
  feature). The burn-test is the user's call (Claude can't operate a phone).

## 5. Risks + mitigations

| Risk | Mitigation |
|---|---|
| P1 breaks gestures we thought worked (e.g. TabBar focus traversal) | Keep `InAppFocusController.attach/detach` lifecycle around (it still owns the click-sound `ToneGenerator` lifecycle); only its `route()` body changes. Behavioural regression tests in InteractionRouterTest. |
| `useSystemKeyEvents = true` default surprises users who expected the old behaviour | The four built-in profiles set this explicitly. Existing user-edited profiles persisted via DataStore default to `true` on first read (forward-compat). |
| `reverseSwipeSemantics` adds a feature flag we'll have to maintain | Accepted — it's one boolean and the user explicitly asked for it. |
| P4 sport-session UX gets too big | Hold scope: just start/stop, live duration + HR, no per-session history in v0.3. History can land in v0.4 when we have multiple workouts to display. |
| P5 spatial features burn battery (`0xA1 [01]` ≈ 64 B/s) | Default OFF. User opts in via Settings → Advanced. The toggle saves to AdvancedPrefs. |
| Doc/02 rewrite drops a piece of info that wasn't actually duplicated in SPEC v3 | Diff Doc/02 §4–6 against SPEC v3 §3–10 line-by-line before deleting; preserve any Halo-Ring-specific calibrations (dedup window, init delay constants) in the new short Doc/02. |

## 6. Acceptance criteria for v0.3.0 release

- All P1–P5 features ship + tests green (`./gradlew :core:test` ≥ 277 cases,
  no failures)
- Both flavor debug APKs build < 16 MB
- Rokid release APK < 5 MB (current 4.1 MB)
- OnePlus burn-test (user-driven):
  - Ring pairs in < 30s end-to-end (Pair → Scan → Connect → bootstrap → READY)
  - SWIPE_UP/DOWN visibly traverses focus on Vitals/Status/Settings tabs
  - TAP fires focused row's onClick (no agent required)
  - Vitals MEASURE NOW yields HR + SpO2 within 30s with snug ring fit
  - Sport session start → live tick → stop works
  - Drop ring (carefully) → HUD shows "Ring dropped?" within 1s
- Doc/02 reduced from 333 → ~100 lines; Doc/17 published as upstream-able
  SPEC v3 fork; new Doc/19 (this) merged

## 7. Out of scope (for v0.3 — defer to v0.4+)

- Sport-session history (workouts log + analytics)
- IMU-based spatial gestures (air-wave, draw-a-circle) — needs the
  `AccelProcessor`'s `WristShake` to land first as proof-of-concept
- Healthcheck composite (`0x69 type=05`) — try again once a firmware update
  fixes the red-LED behaviour observed on this unit
- Cross-glasses hand-over (Rokid ↔ RayNeo) — still blocked on user owning
  both pairs
- Mobile companion app for richer config — D3 in Doc/13's Priority D
- HEALTHCHECK composite when fw supports it (currently the red PPG LED doesn't
  light on this firmware build; SPEC §0.2 notes per-fw working subsets vary)
