## 1. What shipped (v1.1.6)

### 1.1 Home focus — lock-to-first fix (Zack: "概率进主页光标锁死在第一项，往下滑还被抢回第一个")
`HaloRingApp.kt`. The cold-launch focus-anchor loop (`repeat(80){ requestFocus() }`) decided when to
stop via the **async** `contentHasFocus` flag, which has a propagation blind-window: after focus
first landed on row 1, a swipe-down moved to row 2, but the loop — not yet seeing the flag flip —
re-`requestFocus()`'d the **focusGroup**, which always snaps to the FIRST child → cursor yanked back.
- Fix: new `contentReceivedKey` latch. **A DPAD event reaching the content's `onPreviewKeyEvent`
  proves focus is established** (Compose only delivers key events to a focused subtree). On the first
  one, set the latch synchronously (same main-thread dispatch as the `moveFocus`), and the loop exits
  permanently — it never re-requests once the wearer is navigating. The cold-launch "focus landed
  nowhere → re-request" protection is otherwise unchanged (still ~9.6 s budget, exits on
  `contentHasFocus` too).

### 1.2 Mouse attached → focus ring disappears, swiping doesn't bring it back
A pointer device drops the window into Android **touch mode**, which suppresses the Compose focus
highlight. Fix: `LocalInputModeManager.requestInputMode(InputMode.Keyboard)` — called when anchoring
focus AND **on every DPAD `onPreviewKeyEvent`** — so the next ring swipe forces keyboard/focus mode
back and the highlight returns. Applied in both `HaloRingApp` and `FirstRunWizardScreen` (the issue
is global). `requestInputMode` is `@ExperimentalComposeUiApi` → `@OptIn` on both composables.
- **On-glasses verify still pending**: that `requestInputMode(Keyboard)` actually exits touch mode on
  Rokid with a mouse attached.

### 1.3 Keep-alive → direct popup, no "open App info" tail (Zack: 参考 Constellation-Glass)
- **Battery exemption stays the direct system dialog** `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`
  (`package:` Uri → the allow-prompt, not the list) — the **persistent, reboot-durable** grant, like
  Constellation-Glass. Unchanged.
- **The old "background unrestricted / auto-start" wizard gate** that dumped the user into App info to
  hunt for a toggle is **deleted**. That appop is now granted silently by the agent:
  `AdbBootstrap.grantKeepAlive()` = `appops set <pkg> RUN_ANY_IN_BACKGROUND / RUN_IN_BACKGROUND allow`
  (persistent appops), wired into all 3 bootstrap paths (root / pairing / reconnect) + a once-per-
  process self-heal in `refreshSetupState` (covers boot-recovery re-spawn). It deliberately does NOT
  touch the Doze whitelist — battery exemption stays the user's persistent dialog.
- `MainActivity.openAppDetailsSettings()` + `ACTION_APPLICATION_DETAILS_SETTINGS` + the
  `onOpenAutostartSettings` chain + 4 strings: **gone**. KEEP_ALIVE wizard step = battery popup only,
  auto-advances once exempt.

### 1.4 Advanced → state-aware rows + two-tap re-run confirm (Zack: "点击无效是因为已设置好了，要提示")
The Advanced "battery exemption / accessibility / re-run ADB" rows used to silently no-op when the
thing was already done (e.g. `requestBatteryExemption()` early-returns when already exempt → dead
tap, no feedback). Now `SetupActionRow` (reuses `ConfirmCta`'s arm/disarm):
- Shows **live state** — green "✓ …" when satisfied, mute "needs setup" text otherwise. Fed by a new
  `SetupStatus(batteryExempted, accessibilityEnabled, agentReady)` pushed from
  `MainActivity.refreshSetupState` → `HaloRingApp` → `AdvancedScreen`.
- **Already-OK → guarded re-run**: first tap arms (desc → red "Already set — tap again to re-run"),
  second tap within 3 s fires, auto-disarms; a state change disarms it.
- **Not-OK → single tap** runs straight away (don't make the wearer double-tap to fix something).

## 3. Don't-undo list (additions)
- **Focus anchor loop stops on `contentReceivedKey`** — a key event proves focus is placed; don't
  re-add unconditional re-`requestFocus()` (it snaps to row 1 and fights the wearer).
- **`requestInputMode(Keyboard)` on every DPAD event** — that's the mouse/touch-mode focus recovery.
- **Battery exemption = the user's `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` dialog** (persistent /
  reboot-durable). `grantKeepAlive()` does appops ONLY, never the Doze whitelist — don't "simplify"
  it into auto-exempting, or you lose the persistent grant + skip the user confirm.
- **No `ACTION_APPLICATION_DETAILS_SETTINGS` anywhere** — the "find the toggle in App info" tail is
  gone on purpose. The remaining settings-jumps (a11y / overlay / wifi / bluetooth) are necessary —
  Android has no direct-grant dialog for them; the agent auto-grants a11y/overlay when it's up.
