## 1. v0.5 — Wi-Fi-independent agent transport (the big one)

**Problem:** the `app_process` injection agent was bootstrapped over **Wireless Debugging**, which
Android tears down the moment Wi-Fi disconnects (leaving the AP) or on reboot (Wi-Fi off at boot).
So the ring lost system-wide control whenever the user walked away from Wi-Fi.

**Fix (all validated on-device, Wi-Fi OFF + cold reboot, zero user action):**
- The agent now runs over the **legacy plain-TCP ADB port on loopback** (`127.0.0.1:5555`), which is
  Wi-Fi-independent. First-run migrates onto it: `setprop persist.adb.tcp.port 5555` (adbd re-opens
  it on every boot — works on Rokid's `user` build, SELinux enforcing) + `service.adb.tcp.port` +
  `ctl.restart adbd`. Both setprops + ctl.restart are allowed for `shell` (shell_prop). See
  `AdbBootstrap.migrateToPersistentTcp()`.
- `5555` uses the **legacy RSA AUTH** handshake (not STLS) — implemented in `AdbConnection.handleLegacyAuth`
  + `AdbCrypto.signAdbToken` (PKCS#1 v1.5 over SHA1-DigestInfo‖token). The key is added to
  `/data/misc/adb/adb_keys` during wireless pairing, so AUTH passes **silently, no on-device prompt**
  (confirmed from-scratch with a fresh keypair).
- `AdbBootstrap.connect()` prefers `127.0.0.1:5555`, falls back to the wireless TLS port (first-run
  only) then mDNS. `bootRecoverAgent` tries 5555 first and only touches Wi-Fi if unprovisioned.
- **Agent single-owner fix:** `AdbBootstrap` is an `AppGraph` singleton shared by the wizard +
  service, and `bootRecoverAgent` is guarded by a single-flight `Mutex` (two concurrent recoveries
  used to race on the dex push and crash one agent). Wizard pair/reconnect take the same lock via
  `withRecoveryLock`.
- **Wizard:** added a ring-reconnect step (paired+connected → skip; paired+disconnected → reconnect
  w/ short timeout + retry; never-paired → full pair). Removed a dead post-bootstrap "paired" screen
  that stalled fresh setup; added a "turn Wi-Fi off" confirmation gate after the agent migrates.

**Key files:** `adb/AdbBootstrap.kt`, `adb/AdbConnection.kt`, `adb/AdbCrypto.kt`, `di/AppGraph.kt`,
`MainActivity.kt`, `service/HaloRingService.kt`, `ui/screens/FirstRunWizardScreen.kt`.

## 2. v0.5.1 — Bluetooth-internet auto-enable

**Why:** after v0.5 the glasses run with Wi-Fi off, so a second app on the glasses needs internet
via the phone's **Bluetooth tethering (PAN)**. Android resets the per-device **"Internet access"**
toggle on every reboot, and there is **no non-privileged API** to set it (`PanService.connect`
needs `BLUETOOTH_PRIVILEGED`, which neither our app nor the `shell` agent holds — verified on
device). So we **replay the user's manual tap via the AccessibilityService** (the only way without
a privileged signature).

**Where:** Settings → More → **Bluetooth internet** (`BluetoothInternetScreen`):
- **Connect now** — run the flow once.
- **Auto-connect on boot** — pref `AdvancedPrefs.btInternetAutoBoot`; the service runs the flow on
  boot once the phone is media-connected.
- **Open Android settings** — `Settings.ACTION_SETTINGS`.

**The flow** (`HaloRingAccessibilityService.startBtInternetFlow` + `stepBtInternetFlow`): open BT
settings → click the connected phone's gear → scroll to "Internet access" → toggle it on → HUD
notice (`HudEvent.Notice`, posted via `AppGraph.hudNoticeFlow`) → return to app / Home. Hard-won
device facts (Rokid `Connected devices` screen):
- Device selection is **purely structural — no localizable string matching** (Zack's hard rule):
  pick the **top-most on-screen `settings_button`** (resource-id). The connected media phone sits in
  the first ("Media devices") category, so its gear is highest. Requires `flagReportViewIds` +
  `canRetrieveWindowContent` in `halo_ring_accessibility_config.xml`.
- **"Internet access" is below the fold** on the detail screen — the flow scrolls
  (`ACTION_SCROLL_FORWARD`) to reach it. This toggle is the **only** remaining text match
  (`INTERNET_ACCESS_TEXTS`, EN+ZH); no resource-id distinguishes it. Extend the list if a locale fails.
- **First-entry is often unrendered** — right after a reboot the phone briefly sits under "Other
  devices" with no gear; the list only settles after the phone connects as a **media SINK**. So:
  (a) the on-boot trigger waits for `isMediaDeviceConnected()` which checks **A2DP_SINK(11) /
  HEADSET_CLIENT(16)** — the glasses are the *receiver*, NOT A2DP(2)/HEADSET(1); and (b) the flow
  **exits and re-opens** BT settings up to `BT_MAX_REENTRIES` times to force a re-render (Zack's
  insight — was essential).
- **`Mercury_iPhone` is hard-excluded** (`EXCLUDED_DEVICE_NAMES`) — it's a BLE client a phone app
  registers, with no Internet-access toggle. This is the *only* place a device name is matched, and
  only to exclude.

**Key files:** `accessibility/HaloRingAccessibilityService.kt`, `ui/screens/BluetoothInternetScreen.kt`,
`ui/screens/AdvancedScreen.kt` (`AdvancedAction` + `AdvancedPrefs`), `ui/HaloRingApp.kt`,
`ui/hud/HudEvent.kt` + `HudOverlay.kt` (`Notice`), `di/AppGraph.kt` (`hudNoticeFlow`),
`service/HaloRingService.kt` (`isMediaDeviceConnected` + boot hook), `res/xml/halo_ring_accessibility_config.xml`.

**Fragility note:** this is UI automation over the system Settings app — robust today on this Rokid
build, but a Settings UI/locale change can break the "Internet access" text match or the gear
structure. It degrades safely: on failure it shows a HUD reason and returns, never strands the user
in Settings.
