# 11 — v0.4 Design

**Status**: approved 2026-05-27 by Zack. Supersedes [Doc/19](19-v0.3-refactor-plan.md) (parts of it
roll forward — see §10).
**Trigger**: post-burn-in. Real R08_E600 ring + verified SPEC v3 + first day with the live UI
revealed that the current app is built like a phone-style configuration utility, not like a
glasses-native daily-driver. "好像有点过度开发了" — fix it.

This doc is the **canonical decision record** for v0.4. If a future agent disagrees with anything
here, re-open the conversation — they don't silently deviate.

---

## 1. The two pillars

After the burn-in, Zack re-stated the project's purpose in one sentence:

> The project is doing **two things**:
> 1. **Ring as a gesture device** — base gestures satisfy system ops, plus a **large library of
>    custom gestures + plugin extensions** that other apps can hook into. *"自定义手势非常好，
>    一个都别删。"*
> 2. **Full SPEC v3 protocol surface** — every BLE capability we reverse-engineered (vitals,
>    sport, accel, find, battery, activity, capability bitmap, wear-state) should be reachable
>    from the app.

Anything in the codebase that doesn't serve those two pillars is fat to be trimmed. Anything that
*does* serve them — including the parts that look heavyweight — stays.

---

## 2. The diagnosis

### 2.1 What burn-in surfaced

| Finding | Root cause |
|---|---|
| Ring SWIPE_UP/DOWN in the main app does nothing visible | `InAppFocusController` was supposed to remap to Compose focus traversal, but reliably fails to acquire initial focus → ring "都点不出来" |
| Settings menu is unreachable / undiscoverable on glasses | 10+ top-level entries, no visual hierarchy, designed for phone-style scrolling |
| `TestArenaScreen` is a great teaching tool, but you have to *get there* through Settings first | Discovery problem — buried under "use the ring you don't yet know how to use" |
| HUD overlay (the actual highlight) feels great when it appears | ✅ keep |
| Vitals / Status / About / Advanced — full-screen "phone-style" panels eat focus, but the actual data is small | Wrong canvas; data fits in a HUD pip |

### 2.2 What the doc audit confirmed

[Doc/19 §1.3](19-v0.3-refactor-plan.md#13-what-the-doc-audit-confirmed-and-what-surprised-us)
called the v0.3 architecture "fundamentally sound" — that judgment **still holds** for `:core` and
the plugin protocol. v0.4 doesn't touch them. What v0.4 *does* touch is the `:app/ui/` surface.

### 2.3 The mental-model invariant

```
Ring = wireless extension of the temple touchpad.
  - 4 base gestures fire the SAME system KeyEvents the temple does.
  - 8 custom gestures (TRIPLE/QUADRUPLE_TAP, LONG_PRESS, 4 combos) ARE the
    project's value-add — fully programmable via Profile + Plugin Protocol.
```

The 4 base are **hard-locked** in v0.4 (not surfaced in Settings — there's no "rebind TAP"
anywhere). The 8 custom are **richly editable** (Profile Editor / Action Picker / System
Gestures / Gesture Picker all stay).

## 3. What stays — the gems

### 3.1 `:core` (do not touch)

Every file under `app-project/core/src/main/kotlin/com/halo/ring/core/` is load-bearing and
well-tested (282/282 green as of `19f2824` + working tree).

- `GestureSynthesizer.kt` — 4 raw → 12 gesture vocab state machine (28 tests)
- `R08Protocol.kt` + `R08Frame.kt` — SPEC v3-truthified opcodes + parser
- `AccelProcessor.kt` — posture / free-fall / impact / wrist-shake (10 tests)
- `InteractionRouter.kt` — screen-gateway / system / modal / profile layered routing
- `ActionRouter.kt` — backend priority + capability filtering
- `ModeManager.kt` — profile state + auto-switch by foreground app
- `PowerPolicy.kt` — 3-band IntervalMode decision function
- `GlassActionCodec.kt` + `KeyMapProfile.kt` + `DefaultProfiles.kt` — the gesture-binding spine
- `SystemKeyDispatcher.kt` (new in P1) — system KeyEvent dispatch interface
- All `modal/*.kt`, `inject/AgentWireProtocol.kt`, etc.

### 3.2 Plugin Protocol (Doc/10)

External apps register actions via ContentProvider, ring profiles bind to them, gestures trigger
broadcasts. **Constellation already integrates as the first client.** This is the project's
moat. Do not touch.

### 3.3 HUD overlay + 6 event variants (highlight)

`HudOverlay.kt` + `HudEvent.kt` — `WindowManager.TYPE_APPLICATION_OVERLAY` Compose-hosted view,
auto-hide, 6 variants. The **gesture-confirmation pip** and the **gesture-hint HUD** are named by
the user as biggest project highlights. The current 6 events stay; v0.4 *adds* (§5) new ones for
vitals snapshot, sport-tick, spatial alerts.

### 3.4 Custom-gesture editor UI

- `ProfilesListScreen` — list of profiles with active-badge
- `ProfileEditorScreen` — 12-row gesture → action editor (base 4 read-only in v0.4; custom 8 editable)
- `ActionPickerScreen` — grouped action picker (~35 entries + plugin actions)
- `GesturePickerScreen` — 12-gesture picker with conflict warnings
- `SystemGesturesScreen` — 5 system slots (Wake/Sleep/CycleProfile/PeekHUD/AIAssistant)
- `ExternalPluginsScreen` — Doc/10 plugin discovery + binding

These ARE the value-add UI. Custom gestures are the project's biggest feature; the editor cannot
be removed. It just needs to be discoverable and operable on glasses (§7).

### 3.5 SPEC v3 protocol coverage UI

- `VitalsScreen` — HR / SpO2 / steps / cal / distance / ring battery (full data per pillar #2)
- `RingScreen` — MAC / FW / RSSI / battery / find / forget (full data per pillar #2)
- `TestArenaScreen` — gesture training surface (how users learn their custom library)

### 3.6 4-strategy device pattern (Doc/03)

`DisplayAdapter` / `GlassActionMapper` / `WearStateProvider` / `FeatureIntents` — cleanly
abstracts Rokid vs RayNeo. Stays.

## 4. What gets cut or shrunk

| Item | Action | Why |
|---|---|---|
| `InAppFocusController` | **DELETE** | Root cause of "ring 点不出来". Standard Compose `FocusManager` + system KeyEvents (P1) handle DPAD natively. |
| `TempleFocusBridge` | **DELETE** | Same reasoning — the temple's KeyEvents come via the system anyway; we don't need a bespoke bridge. |
| `FirstRunWizardScreen` (5 steps) | **Collapse to 1 step (pair ring)** | ADB / A11y / Battery / Welcome steps are over-engineered for daily use. Pair = the only required step. |
| `GuidedTour.kt` | **DELETE** | Test Arena does the same job better, on demand. |
| `AdvancedScreen` | **Shrink** to: rerun ADB wizard, export logs, toggle "spatial features" | All the placeholder toggles (debug HUD, latency, spatial) move out — debug HUD becomes always-on dev-build, latency becomes always-tracked, spatial becomes a single Settings → Vitals item. |
| `AboutScreen` | **Shrink to 3 rows**: version, device, "license: AGPLv3 + commercial" | Was already slimmed once in audit-pass-u; can go further. |
| `PowerConnectionScreen` (3 timing windows + 3 toggles) | **Collapse to defaults + 1 "advanced timings" expander** | Most users will never touch these; defaults are tuned in `DefaultProfiles`. |
| `StatusScreen` full-screen | **Convert to HUD overlay** triggered by `PEEK_HUD` system gesture | Status is by definition glanceable, not navigable. |
| `SettingsRootScreen` (10+ flat items) | **Reorganise into 5 groups** (Ring / Vitals / Gestures / Plugins / More) | Doc/19 P2 was right — carries forward. |
| `LanguageScreen` | Move into More → Language (no change other than location) | Fine where it is functionally. |

Net delta: ~27 screens → ~20 screens, plus aggressive shrinking inside the survivors.

## 5. The HUD becomes the daily UX surface

The HUD overlay is now the **primary daily UX**. The Activity is where you go for
*configuration*, not for daily use. Mirrors Constellation-Glass's "Service spine + HUD-first"
philosophy.

### 5.1 Existing HUD events (keep, may polish)

| Event | When |
|---|---|
| `GesturePip` | Right after `GestureSynthesizer` commits a gesture — shows the gesture name + bound action; 1.5 s auto-fade |
| `ProfileSwitched` | When `ModeManager` switches profile (manual cycle or auto-trigger); 2 s |
| `VitalsHrTick` | HR-on-HUD if the user opts in via Vitals prefs |
| `Disconnected` | Ring disconnect; 60-s reminder (per audit-pass-l) |
| `Reconnecting` | Ring reconnecting; pulses |
| `Connected` | Ring connect; 1 s |

### 5.2 New HUD events for v0.4

| Event | When |
|---|---|
| `VitalsSnapshot` | After user fires the bound "MeasureVitals" action; 3 s display of final HR/SpO2 + auto-fade |
| `SportTick` | During an active sport session — minimal pip showing duration + HR; 8 s |
| `SpatialAlert` | `AccelProcessor.FreeFall` → "Ring dropped?" / `WristShake` if bound; 2 s |
| `PluginCard` | Plugin pushes a transient card via PROFILE_PUSH; lifetime controlled by plugin |

### 5.3 HUD canvas constants

- **480×640 portrait** per [Rokid bare-metal §00](../../Constellation/reference/rokid-glass/bare-metal-docs/00-overview.md).
  Doc/05 currently says 480×480 — that's wrong, fix during the v0.4 doc/code pass.
- Black canvas (additive see-through = unlit = transparent).
- HUD pip in upper-right (Halo) or upper-left (configurable per `hudPosition`), 320×120 pip target.
- Lower-right reserved for Constellation's pip when Constellation is also running (it agreed to
  take upper-band only — see `GLASS-CLIENT-DESIGN.md` §1.4).

secondary — it's where you go for configuration, and `MainActivity.onResume` doesn't drive

### 6.1 Rokid temple input — system ordered broadcasts (NOT Activity onKeyDown)

Per [`bare-metal-docs/01-key-events.md`](../../Constellation/reference/rokid-glass/bare-metal-docs/01-key-events.md),
Rokid Glasses publish all temple actions as **system ordered broadcasts** plus standard KeyEvents
on the foreground Activity. The broadcasts work in a `Service` without a foreground Activity —
which is critical because Halo Ring's Activity is rarely visible.

Broadcasts to register on `HaloRingService`:

| KeyType | Action constant | Role for Halo Ring |
|---|---|---|
| `CLICK` | `ACTION_SPRITE_BUTTON_CLICK` | Confirm focus (same as DPAD_CENTER) |
| `DOUBLE_CLICK` | `ACTION_SPRITE_BUTTON_DOUBLE_CLICK` | Back (system-occupied, can't abort — that's fine, ring DOUBLE_TAP matches) |
| `LONG_PRESS` | `ACTION_SPRITE_BUTTON_LONG_PRESS` | Mirror of ring LONG_PRESS — for users without a ring |
| `ACTION_TWO_FINGER_SINGLE_TAP` | `ACTION_TWO_FINGER_SINGLE_TAP` | Mirror of ring DOUBLE_TAP-as-confirm in some profiles |
| `ACTION_TWO_FINGER_SWIPE_FORWARD` | `ACTION_TWO_FINGER_SWIPE_FORWARD` | Mirror of SWIPE_UP |
| `ACTION_TWO_FINGER_SWIPE_BACK` | `ACTION_TWO_FINGER_SWIPE_BACK` | Mirror of SWIPE_DOWN |
| `ACTION_SETTINGS_KEY` | `ACTION_SETTINGS_KEY` (二指长按) | Hint: open Halo Ring Settings (the only place where it's legitimate) |

Two reasons to use broadcasts not Activity.onKeyDown:
1. **No Activity foreground required.** Service receives broadcasts from anywhere.
2. **Symmetry with the ring.** Ring events come via BLE notifications, also Service-handled. The
   two input sources unify into the same `InteractionRouter` pipeline.

`abortBroadcast()` at `priority=100` is available for **non-system-occupied** broadcasts (CLICK,
LONG_PRESS, TWO_FINGER_*). DOUBLE_CLICK is system-occupied for back and we don't want to
intercept it anyway.

### 6.2 Activity is for configuration, not for running

`MainActivity` (renamed to `ConfigActivity` in spirit, though renaming is optional)
opens on icon-tap and on `ACTION_SETTINGS_KEY`. It shows the 5-section Settings + the
custom-gesture editor + Vitals dashboard. It does NOT manage:

- BLE state (Service owns it)
- HUD lifecycle (Service owns it)
- Gesture pipeline (Service owns it)
- System KeyEvent dispatching (Service owns it via the broadcast path)

So if the Activity is never opened after pairing, the app still works perfectly. **That is the
test of v0.4 success.**

## 15. Risk register

| Risk | Mitigation |
|---|---|
| Deleting `InAppFocusController` breaks some focus scenario we didn't anticipate | C1 includes a smoke check on each config screen with the ring; standard Compose FocusManager + system KeyEvents covers everything we tested |
| `SystemBroadcastReceiver` (§6.1) conflicts with Sprite Launcher's own consumers | Use `priority=100`; only `abortBroadcast()` the actions we explicitly intend to consume; leave DOUBLE_CLICK alone (system-occupied) |
| Settings reorganisation hides a feature a power-user used to know how to find | Migration: all old prefs keys + DataStore unchanged; only the navigation UI moves. Document the new path in Doc/06 user manual. |
| User invariant changes again (e.g. "actually I want to rebind TAP") | The 4-base hard-lock is one boolean (`useSystemKeyEvents` in `GestureConfig`); flipping it via DataStore is a one-liner. Don't expose in Settings UI in v0.4 per Zack's explicit invariant. |

### On-glasses iteration deltas (beyond the original plan)

These came from burn-in on the actual glasses and supersede parts of §3-§9 where they differ:

1. **Base-gesture KeyEvent mapping — dual-axis swipe.** `SWIPE_UP → [DPAD_UP, DPAD_LEFT]`,
   `SWIPE_DOWN → [DPAD_DOWN, DPAD_RIGHT]` (was single vertical key). Reason: the Rokid app list
   is **horizontal** (needs LEFT/RIGHT) while home/notifications/in-app are vertical — emitting
   both axes navigates either; only the axis with a focusable neighbour moves. Mirrors the temple
   swipe. `TAP → DPAD_CENTER` (Rokid temple click actually emits `KEYCODE_ENTER`, which Compose
   `clickable` also handles), `DOUBLE_TAP → BACK`.
2. **LONG_PRESS = screen toggle.** `SystemGestures.sleep` default changed to `LONG_PRESS` — so
   LONG_PRESS **wakes** (screen off) and **sleeps** (screen on): one easy, common gesture.
   Replaces the fiddly `LONG_PRESS_SWIPE_DOWN`-for-sleep and the old `LONG_PRESS→Menu`. Shadows
   the per-profile LONG_PRESS while screen-on (rebind the SLEEP slot to restore). Window cut to
   **60 ms** (`longPressFollowupWindowMs`) so it's near-instant after the firmware's ~600 ms
   hold-to-register floor (which is hardware, unchangeable).
3. **WRIST_SHAKE air-gesture wired** (the protocol goldmine). New `Gesture.WRIST_SHAKE` —
   `AccelProcessor` already detected it; now it's a real, bindable gesture routed through the
   profile (default → AI assistant on Nav/Media, AI chat on Reader), shown in the gesture picker +
   Test Arena, with its own sound. **Requires the accel stream** → opt-in via Settings → Vitals →
   Spatial features (gated to worn + screen-on for energy).
4. **Per-gesture sound effects** (`GestureSounds`) — distinct ToneGenerator tone per gesture for
   eyes-off confirmation; gated by the "UI click sound" feedback pref.
5. **Combo windows retuned for trainability** — `multiTapWindowMs 280→300`, `comboWindowMs
   300→400` (DOUBLE_TAP_SWIPE was committing as bare DOUBLE_TAP=Back before the swipe landed).
6. **Fast profile dropped** — post-v0.4 the base gestures are already instant system KeyEvents +
   long-press is near-instant, so Fast's "low-latency, no-combos" value became the default.
   `DefaultProfiles.ALL = [Navigation, Media, Reader]`.
7. **Energy (from the audit):** BLE auto-reconnect now uses **exponential backoff** (800 ms→30 s,
   resets on READY) instead of a back-to-back LOW_LATENCY scan loop; the **accel stream is gated**
   on worn + screen-on, not always-on. `connectGatt(autoConnect=false)` cut first-connect from
   ~57 s → ~3 s.
8. **CompositeSystemKeyDispatcher** — base gestures dispatch to the foreground Activity window
   when Halo Ring is foreground, else inject system-wide via the agent (`InputManager`). This is
   what lets the ring drive **other** apps on the glasses.
9. **Wizard reworked** — strict sequential single-button gate (dev-options → wireless-debug →
   pair), no Skip, agent-already-running detection, auto-enter on lost-perms at startup, jump to
   Build-number screen + auto-enable dev-options/wireless-debug if `WRITE_SECURE_SETTINGS` held.
   Keep-alive step (battery exemption auto-request + background-unrestricted guidance).

### Verified on the actual Rokid Glasses

- App runs as a Service; pairing → fast connect (~3 s) → READY + 17 capabilities decoded.
- **Agent proven on real Rokid hardware** (`app_process` → `InputManager.injectInputEvent`,
  `LocalServerSocket("halo.agent")` listening, heartbeat fresh, `WRITE_SECURE_SETTINGS` granted via
  `pm grant`). **NOTE: it was bootstrapped via USB as a dev shortcut** — the *wireless* pairing
  flow (`AdbPairingOverlay` 6-digit code) is the only piece NOT yet validated on Rokid, and
  reboot-survival (`bootRecoverAgent`) needs that wireless trust established first. **This is the
  top open item.**
- Temple click = `KEYCODE_ENTER`, double-click = `KEYCODE_BACK`; temple single-finger swipe fires
  `KEYCODE_NOTIFICATION` (not DPAD) — so the **ring** (not the temple) is the nav device.
